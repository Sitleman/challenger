# Stage, production и выпуски v1, v2, …

## Поток

Merge в `master` → CI → сборка и публикация образа в GHCR → присвоение `vN` →
aвтоматический stage → проверка готовности → сообщение в stage-чат.
`Prepare production release` собирает черновик за диапазон от текущего prod до
выбранной stage-версии. После редактирования текста `Promote production`
фиксирует образ и сообщение в артефакте workflow, показывает их в Summary и
ожидает approval пользователя `Sitleman` в environment `production`.

В prod запускается тот же digest, который успешно работал на stage. Новые мерджи
не меняют утверждаемый артефакт. При смене prod-версии за время ожидания деплой
отклоняется: заново подготовить выпуск, проверить текст и дать новый approval.

Бизнес-схема SQLite не меняется. Контуры используют разные токены Telegram,
разные чаты, тома, Compose projects и каталоги состояния. Продовый бот должен
быть удалён из stage-чата или ограничен только продовым chat ID.

## Номера и состояние

Аннотированные git-теги `vN` хранят commit, digest образа и снимок записей changes.
Номер выделяется после успешной публикации образа, под общей блокировкой workflow.
Повторная попытка для того же commit использует прежний номер и digest.
Номер не переиспользуется, даже если stage-деплой не удался. Пропуски допустимы.
GitHub concurrency может заменить ожидающую выкладку более новой; сервер также
отклоняет версию старше установленной. Это не гарантирует выкатку каждого merge.

GitHub Release для версии первоначально является draft. `stage.json` в его assets
подтверждает успешную stage-выкатку. `candidate.json` фиксирует исходную prod-версию
при подготовке. Тело draft редактируется человеком. После freeze дальнейшие правки
draft не влияют на ожидающий approval запуск; чтобы изменить сообщение, отменить
ожидающий запуск и запустить Promote заново.

После успешной prod-выкатки сохраняется `production.json`, обновляется служебный
тег `deployed-production` и публикуется GitHub Release. Тег отражает именно текущую
prod-версию, в том числе после ручного отката; номер последнего созданного релиза
для этой цели не используется.

Сервер хранит фактическую версию в `/var/lib/challenger/<environment>/current.json`.
Бэкапы, незавершённая операция и квитанции отправок находятся рядом, вне SQLite-тома.
Удаление git-тегов или изменение release assets ломает историю; ограничить права
на такие операции. Не удалять опубликованные образы, пока они нужны для отката.

## Однократная настройка GitHub

До завершения настройки `RELEASE_ENABLED` должен отсутствовать или быть `false`.
CI и проверка изменений работают, публикация и деплой отключены.

Создать environments:

| Настройка | stage | production |
|---|---|---|
| Deployment branches | Только `master` | Только `master` |
| Required reviewers | Нет | Только `Sitleman` |
| Prevent self-review | Выключено | Выключено |
| Allow administrators to bypass | Выключено | Выключено |
| Variables | `DEPLOY_HOST`, `DEPLOY_USER` | `DEPLOY_HOST`, `DEPLOY_USER` |
| Secrets | `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` | `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` |

`DEPLOY_KNOWN_HOSTS` — проверенный заранее публичный host key сервера. Во время
деплоя не использовать доверие к результату нового `ssh-keyscan`.
SSH-пользователь — root; ключи двух контуров отдельные и обязательно ограничены
forced command, как описано ниже. Не выдавать Actions обычный root-shell.
Не помещать SSH-секреты в repository secrets. Freeze проверяет required reviewer
и запрет обхода; отсутствие защиты приводит к отказу, а не к автоматическому prod.

Repository variables:

- `RELEASE_BASE_SHA` — полный commit фактической prod-версии перед первым CI-релизом.
  Это не обязательно HEAD checkout. Сверить с существующим `deployed.commit`.
- `RELEASE_ENABLED=true` — включить только после подготовки обоих контуров.

Защитить `master`: PR и успешные `test`, `lint`, `docker`, `release-tests` обязательны.
Продвижение разрешено только `Sitleman` из основной ветки. Merge выполняет человек.
GHCR publication использует `GITHUB_TOKEN` с `packages: write`. Если package private,
на сервере заранее выполнить `docker login ghcr.io` отдельным токеном только с
`read:packages`; токен не записывать в репозиторий или логи. Дать package доступ Actions
этого репозитория. Сборка рассчитана на Linux amd64, как GitHub runner.

## Однократная подготовка сервера

Нужны Docker Compose, Python 3.12+, GNU/Linux и два отдельных Telegram-бота.
Серверный обработчик устанавливается администратором из проверенной версии этого
репозитория в `/opt/challenger-deployer`: нужны `scripts/release/*.py` и
`deploy/compose.yml` с сохранением структуры каталогов, владельцем root и без
права записи другим пользователям. Обновлять обработчик отдельно после ревью;
Actions не может загрузить или исполнить собственный скрипт на сервере.

В `/root/.ssh/authorized_keys` добавить два различных публичных ключа:

```text
restrict,command="/usr/bin/python3 /opt/challenger-deployer/scripts/release/entrypoint.py stage" ssh-ed25519 <stage-public-key>
restrict,command="/usr/bin/python3 /opt/challenger-deployer/scripts/release/entrypoint.py production" ssh-ed25519 <production-public-key>
```

Ключ stage принимает только `deploy stage` и `notify stage`, ключ production —
только команды своего контура. Манифест передаётся через stdin; scp, shell,
port forwarding и запуск произвольных файлов недоступны. Обработчик допускает
только digest образа `ghcr.io/sitleman/challenger`. Даже на общем сервере stage-ключ
не получает доступ к prod-конфигурации. Настройка Docker, перенос действующего prod
и создание stage-бота выполняются отдельно.

Создать конфигурации с правами `600`, каталоги с правами `700`:

`/etc/challenger/stage.env`:

```dotenv
BOT_TOKEN=<токен отдельного stage-бота>
ALLOWED_CHAT_IDS=-1004391088785
ADMIN_USER_IDS=532029049
CHALLENGE_TZ=Europe/Moscow
```

`/etc/challenger/production.env` — те же ключи, но продовый токен и
`ALLOWED_CHAT_IDS=-1003436893374`. Использовать простые `KEY=value`, без подстановок
shell, многострочных значений и inline-комментариев. Секреты остаются на сервере.

`/etc/challenger/stage.json`:

```json
{
  "project": "challenger-stage",
  "volume": "challenger-stage-data",
  "env_file": "/etc/challenger/stage.env",
  "chat_id": -1004391088785
}
```

`/etc/challenger/production.json`:

```json
{
  "project": "challenger",
  "volume": "challenger-data",
  "env_file": "/etc/challenger/production.env",
  "chat_id": -1003436893374
}
```

Для сообщения в определённую тему форума добавить `thread_id` в JSON.
Stage-бота добавить только в stage-чат. Списки ALLOWED_CHAT_IDS проверяются перед
выкаткой: разрешён ровно чат данного контура. Токены двух ботов должны отличаться.

Существующий production project `challenger` и том `challenger-data` сохраняются:
новый Compose подхватит действующий сервис `bot`. Проверить имя project через labels
работающего контейнера перед включением. Второй prod-контейнер запускать нельзя.

Stage-том создать отдельно, сразу с владельцем UID/GID 65532, иначе nonroot-образ
не сможет создать SQLite. Например, создать volume и сменить владельца его
Mountpoint на сервере. Prod-том не очищать и не копировать в stage автоматически.

В каждом `/var/lib/challenger/<environment>/current.json` записать исходное состояние:

```json
{
  "version": "v0",
  "commit": "<полный commit до включения CI/CD>",
  "image": "<сохранённый локальный тег текущего образа>",
  "entries": {}
}
```

Для prod предварительно присвоить работающему image ID постоянный локальный тег,
например `challenger-bot:bootstrap`; использовать его в `image`. Для пустого stage
допустим такой же тег: при первом деплое контейнер по нему не запускается.
`v0` — только исходное состояние, пользовательские выпуски начинаются с `v1`.
Создать отдельный исходный бэкап prod по старой инструкции перед включением.

Первую выкатку наблюдать вручную: stage → сообщение → Prepare → редактирование draft →
Promote → Summary → approval → prod → сообщение. Код не проверяет семантику новых
возможностей: на stage её проверяет человек до продвижения.

## Обычный выпуск

1. В PR добавить запись в `changes/` по [формату](../changes/README.md).
2. После merge дождаться stage-job и проверить бота, включая `/version`.
3. В Actions запустить `Prepare production release`, указав, например, `v5`.
4. Открыть draft GitHub Release по ссылке из Summary. Отредактировать его тело:
   объединить связанные пункты, убрать отменённые возможности. Не публиковать вручную.
5. Запустить `Promote production` с той же версией, посмотреть Summary freeze-job.
6. Нажать Review deployments → production → Approve.

Если prod был `v1`, а stage прошёл `v2`, `v3`, `v4`, `v5`, черновик `v5` содержит
все новые записи после `v1`. Каждая версия не требует отдельного prod-релиза.

## Ошибки, повторные запуски и откат

Скачивание образа происходит до остановки. Затем бот останавливается, том целиком
архивируется, новый контейнер запускается и до 120 секунд ожидается healthcheck.
Готовность означает успешный свежий getUpdates после открытия БД и миграций,
отсутствие рестартов. При ошибке до запуска новой версии прежний контейнер
возвращается. Если новая версия не прошла проверку, она останавливается;
`pending.json` блокирует следующие выкладки до ручного восстановления.
Автоматического отката БД нет: это могло бы потерять уже принятые сообщения.

Повторный deploy той же версии только проверяет готовность. После успешного deploy
и сбоя GitHub/Telegram повторить упавшие jobs текущего workflow. Они используют тот
же артефакт и не выполняют повторную миграцию или перезапуск. Если prod уже записан
в GitHub, не запускать Prepare для той же версии — повторить исходный job.

Успешная отправка записывает Telegram message ID в `notifications/vN-<chat>.json`.
Явный отказ API допускает повторную отправку после устранения причины.
При таймауте квитанция остаётся `sending`: проверить чат. Если сообщение есть,
вручную сохранить `status: sent` и `message_id`; если точно не отправлено — сменить
статус на `rejected` и повторить job. Не сбрасывать `sending` вслепую.

Ручной откат возвращает образ и БД вместе. Все сообщения/изменения БД после снимка
могут быть потеряны; текущий том сохраняется в `before-restore-*`. Выбрать каталог
бэкапа из `pending.json` или `backups/`, затем из проверенной копии репозитория:

```bash
python3 scripts/release/server.py rollback production <имя-каталога-бэкапа>
```

Скрипт требует сохранённый предыдущий образ на сервере. Он восстанавливает владельца
файлов 65532 и ждёт готовности. Для исходной `v0`, не имевшей healthcheck, дополнительно
вручную выполнить проверку запуска из старой инструкции.

После отката скопировать серверный `current.json` в локальный `release.json` и для
версии `v1` или новее выполнить с авторизацией GitHub и `GITHUB_REPOSITORY`:

```bash
python3 scripts/release/github.py production-success
```

Это синхронизирует `deployed-production` с фактическим prod. Для возврата к исходной
`v0` удалить только служебный тег `deployed-production`, восстановить правильный
`RELEASE_BASE_SHA`. Не удалять теги `vN`. До синхронизации не готовить новый выпуск;
сервер в любом случае отклонит кандидат с неверной исходной prod-версией.
Rollback не отправляет старый changelog повторно и не выделяет новый номер.
