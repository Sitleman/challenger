# 0003 — Бэкап базы: снимок в Telegram, восстановление подкомандой

**Дата:** 2026-10-25
**Статус:** принято
**Issue:** #13

## Контекст

База — один файл SQLite в WAL на томе `/data` (ADR 0002, #12). Бэкапов не было, кроме
ручного `tar` тома при остановленном боте. Нужен ежедневный бэкап без участия человека,
бэкап по запросу и понятное восстановление. Образ distroless: внутри нет shell, `cron`
и `sqlite3`.

## Решение

- Снимок делает сам бот: `VACUUM INTO` во временный каталог рядом с базой, затем
  `PRAGMA integrity_check`. Ежедневно в 04:00 по `CHALLENGE_TZ` и по `/make_backup`
  в личке от id из `ADMIN_USER_IDS`.
- Хранилище — Telegram: бот присылает файл документом каждому доверенному в личку.
  Локальных копий нет.
- Восстановление — подкоманда `challenger restore <файл>`. Порядок такой:
  - копия бэкапа переводится в rollback-журнал и проверяется: целостность и версия
    goose не новее бинаря;
  - текущая база вместе с `-wal`/`-shm` переименовывается в `.before-restore-<время>`;
  - копия встаёт на место базы.
- Бот держит `flock` на `DB_PATH.lock`, `restore` без этой блокировки не работает.

## Почему

- Копия файла WAL-базы без `-wal` теряет последние записи, а `VACUUM INTO` даёт
  согласованный самодостаточный файл и не останавливает бота.
- Telegram не требует ни новой инфраструктуры, ни ключей: токен у бота уже есть,
  а файл лежит вне сервера. База одной команды весит килобайты, до лимита
  `sendDocument` в 50 МБ далеко.
- Подкоманда работает в distroless через `docker compose run`. Блокировка отличает
  «бот остановлен» от «бот работает» надёжнее, чем доступ к файлу базы: в WAL
  простаивающий бот не держит блокировок SQLite.

## Следствия

- Бэкап получает только тот доверенный, кто хоть раз написал боту `/start`.
- Если бот был выключен в 04:00, бэкап за этот день пропускается.
- Два бота на одной базе теперь не стартуют: второй падает на блокировке.
- Если база перерастёт 50 МБ, понадобится другое хранилище, например S3.
