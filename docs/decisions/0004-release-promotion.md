# 0004. Продвижение неизменяемого образа со stage в production

## Контекст

Боту нужны отдельные stage/prod-чаты, автоматический stage после merge, личный
approval prod и понятное сообщение об изменениях. Несколько stage-версий могут
быть пропущены в production. Ранее образ собирался на сервере с 1 CPU/1 ГБ RAM;
обновление и согласованный бэкап SQLite выполнялись вручную.

## Решение

Собирать в GitHub Actions, сохранять digest в аннотированном теге `vN`, продвигать
этот digest. Одна последовательность номеров, без major/minor и переименования
при продвижении. Повторные попытки одного commit используют ту же версию.

Изменения для пользователей входят в PR отдельными неизменяемыми JSON-фрагментами.
Draft Release позволяет отредактировать объединённый changelog от текущего prod
до выбранного кандидата. Перед environment approval замораживаются образ,
исходная prod-версия и текст в immutable artifact конкретного workflow run.

Рабочая SQLite, состояние выкладки и квитанции Telegram разделены. После проверки
готовности сначала фиксируется фактический деплой, затем отправляется сообщение.
Сбой доставки не откатывает приложение. Неоднозначная отправка требует проверки
чата, поскольку Telegram sendMessage не предоставляет ключ идемпотентности.

Том архивируется при остановленном боте. Ошибка новой версии блокирует дальнейшие
выкладки до восстановления; автоматически возвращать старую БД нельзя из-за риска
потери уже принятых сообщений. У контуров разные токены и тома. SSH-ключи ограничены forced command своего
контура; серверный обработчик устанавливает администратор. Actions передаёт
только манифест, поэтому stage-ключ не даёт root-shell и не обходит prod approval.

## Почему

Это сохраняет человеческий контроль над prod и текстом, не требует повторной
сборки проверенного образа, не зависит от числа пропущенных stage-версий и не
превращает перезапуск бота в повторное объявление релиза. JSON-фрагменты читаются
стандартной библиотекой Python без зависимости от YAML-парсера на сервере.

Локальный прецедент — [PR #31](https://github.com/Sitleman/challenger/pull/31):
согласованный бэкап остановленного SQLite-тома, проверка getUpdates и отдельный
учёт фактически развёрнутой версии. Поиск: история `docs/deploy.md` и текущие
`.github/workflows`; других механизмов деплоя в репозитории нет.

Операционная инструкция — [releases.md](../releases.md).
